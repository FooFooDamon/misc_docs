# 1、背景

## 1.1 问题

* **标准的**`Modbus-RTU`**协议数据单元**（`Protocol Data Unit`，简称`PDU`）模型**无法**简洁、
有效地**表示**`业务层`异常。

## 1.2 构想

* 在**兼容原有**的`Modbus-RTU`协议体系的前提下进行**适当的扩展**，
使**业务层**逻辑的**简洁表示**以及**高效执行**成为可能。

* **提取**出**业务无关**的**顶层规则**载于本文档，业务相关的协议明细项需另建文档，
且其制定要受本文档规则的约束。

# 2、设计详情

## 2.1 原始标准提要

* **数据模型**（`Data Model`）根据数据的**位宽**和**读写权限**进行**组合**，
分成`4`类（注意只是**建模层面上的含义**，并不是对具体业务的硬性限制）：
    * `离散输入`（`Discrete Input`）：单个比特；只读。
    * `线圈`（`Coil`）：单个比特；可读可写。
    * `输入寄存器`（`Input Register`）：`16`位字；只读。
    * `保持寄存器`（`Holding Register`）：`16`位字；可读可写。

* **功能码**（`Function Code`）分类：
    * **公共**功能码：范围为`[1, 64]`、`[73, 99]`、`[111, 127]`。注：里面有少数`预留`码，但本文档不关注。
    * **用户自定义**功能码：范围为`[65, 72]`、`[100, 110]`。

* **帧**（`Frame`）、**应用数据单元**（`Application Data Unit` -> `ADU`）、
**协议数据单元**（`Protocol Data Unit` -> `PDU`）之间的关系：
    * `Frame` = `ADU` = `从机地址` + `PDU` + `校验码`
    * `PDU` = `功能码` + `数据域`

* 以两个常见的功能码为例，说明`PDU`格式的一般规律：

    * **读**取**多个**寄存器（功能码**0x03**，差错码`0x83` = 功能码 `|` `0x80`）：

        | 帧类型 | `PDU`格式 |
        | ------ | ------ |
        | 请求   | 功能码 + 起始**地址** + 寄存器**数量** |
        |                                                 |
        | 正常响应 | 功能码 + **字节数** + 寄存器**值列表** |
        |                                                   |
        | 异常响应 | **差错码** + 异常码 |

    * **写**入**多个**寄存器（功能码**0x10**，差错码`0x90` = 功能码 `|` `0x80`）：

        | 帧类型 | `PDU`格式 |
        | ------ | ------ |
        | 请求   | 功能码 + 起始**地址** + 寄存器**数量** |
        |        |        + **字节数** + 寄存器**值列表** |
        |                                                   |
        | 正常响应 | 功能码 + 起始**地址** + 寄存器**数量** |
        |                                                   |
        | 异常响应 | **差错码** + 异常码 |

* 从前一点可以看出，**异常**响应与**正常**响应**截然分开**，不同时发生，
也意味着**两者承载的信息不能同时获取**。

* 只提供**极少**的**异常码**，且**不允许用户进行扩展**，因此难以反映业务层的异常状况，
再与前一点结合就更加加重施加在业务层的局限性。

* 其他要点：
    * **字节序**：
        * 从机地址、`PDU`：采用**大**端（`Big-Endian`）字节序，即**先**发**高**字节、**后**发**低**字节。
        原因：符合人类阅读习惯。
        * `CRC`：采用**小**端（`Little-Endian`）字节序，即**先**发**低**字节、**后**发**高**字节。
        原因：为适配“低位先行”的串行移位运算，大幅**降低**了**早期**嵌入式**设备**的`CRC`**计算开销**。
    * 帧间隔与停止位的规定：
        * 帧**间**最**小**间隔：
            * 波特率 < `115200`时：大于等于`3.5`个字符的传输时间。
            * 波特率 >= `115200`时：固定为`1.75ms`。
        * 帧**内**最**大**间隔：`0` <= t <= `1.5`个字符的传输时间。
        * **停止位**：以“能把**字符总位数**补足到恒定的**11**位”为准则，以便**统一**“帧间隔”的**计时基准**，因此：
            * 有奇偶校验时：`1`个停止位。
            * **无校验**时：**2**个停止位。
            * 注：很多设备并不严格遵守此项规范，即使是无校验也只用`1`个停止位，因此要以双方约定为准。

## 2.2 扩展方案

### 2.2.1 方案内容

由前一节的内容能推知，要令业务层逻辑能简洁地表示以及高效地执行，可以考虑以下设计：

* 不严格区分数据是按位操作还是按字操作，也不区分是只读还是可读可写，**一律**看成**保持寄存器**即可。

* 由于**操作多个寄存器**的协议格式**普适性更强**，且实际场景也经常有此类需求，
所以可以在功能码**0x03**和**0x10**的基础上进行扩展，功能码则在用户自定义区块内任选两个。

* **增加**一个**字段**来表示**业务层异常**，同时**协议层异常**也可以**合并进来**，
一齐**在正常响应呈现出来**（不再使用异常响应），这对于部分出错仍要返回其余正常数据的场景非常合适。

* 如果从机有多通道，还可以增加一个字段（或者在异常码和通道数都很少的情况下合并到上一个字段），
利用该**字段内**的**二进制位**来**指示**是**哪个通道有异常**。

* 扩展示例（仅需改造响应`PDU`格式，请求`PDU`还是沿用**0x03**和**0x10**功能码原有的格式）：

    * 读寄存器响应：

        ````
        16通道且异常情况较少时：
        +---------------------------------------------------------------+
        | 字段含义 | 功能码 | 异常码 | 通道指示 | 字节数 | 寄存器值列表 |
        |---------------------------------------------------------------|
        | 字节数   |   1    |   2    |    2     |   1    |    2 x N     |
        +---------------------------------------------------------------+
        或8通道且异常较多时：
        +-----------------------------------------------------------------------------------------+
        | 字段含义 | 功能码 | 全通道异常指示高位字 | 全通道异常指示低位字 | 字节数 | 寄存器值列表 |
        |-----------------------------------------------------------------------------------------|
        | 字节数   |   1    |           2          |           2          |   1    |    2 x N     |
        +-----------------------------------------------------------------------------------------+
        ````

    * 写寄存器响应：

        ````
        16通道且异常情况较少时：
        +---------------------------------------------------------------+
        | 字段含义 | 功能码 | 异常码 | 通道指示 | 起始地址 | 寄存器数量 |
        |---------------------------------------------------------------|
        | 字节数   |   1    |   2    |    2     |    2     |     2      |
        +---------------------------------------------------------------+
        或8通道且异常较多时：
        +--------------------------------------------------------------------------------------------------+
        | 字段含义 | 功能码 | 异常码 | 全通道异常指示高位字 | 全通道异常指示低位字 | 起始地址 | 寄存器数量 |
        |--------------------------------------------------------------------------------------------------|
        | 字节数   |   1    |   2    |           2          |           2          |     2    |     2      |
        +--------------------------------------------------------------------------------------------------+
        ````

    * 异常码（`0`表示正常，非`0`表示有异常发生）：

        ````
        // 最低3位兼容原先的协议层异常
        Bit[2:0]：
            * 001：非法功能码
            * 010：非法地址
            * 011：非法数据值
            * 100：从机设备故障
        // 从Bit3开始是业务层异常，可以每一位对应一种异常，也可以多位一齐使用从而对应多种异常的组合
        Bit[3]：是否有校验异常
        Bit[4]：是否查询电流失败
        Bit[5]：是否查询电压失败
        Bit[6]：是否查询温度失败
        Bit[7]：是否查询压力失败
        .
        .
        .
        // 其他自定义异常
        ````

    * 通道指示字段：

        ````
        Bit[0]：是否与通道1有关
        Bit[1]：是否与通道2有关
        Bit[2]：是否与通道3有关
        .
        .
        .
        Bit[15]：是否与通道16有关
        ````

    * 全通道异常指示字段（高位字与低位字合并得到一个`32`位字）：
        * 高`8`位：即前面的通道指示字段，只是能表示的通道数量不同
        * 低`24`位：异常码，定义方法可参考前面的异常码内容

### 2.2.2 普适性分析

* **单**通道**单**寄存器：完全适用。

* **单**通道**多**寄存器：完全适用。

* **多**通道**单**寄存器：完全适用。

* **多**通道**多**寄存器：无法完全指出哪些通道的哪些寄存器出现哪些异常，
需要为每个寄存器选定一个值（例如`0xFFFF`）用来表示异常情况，这样才能准确定位异常源。
